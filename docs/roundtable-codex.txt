# Project Guidelines

## When to Use This Skill

- At the start of every Claude Code session, as baseline behavioral guidelines
- When the user wants consistent communication and progress reporting behavior
- When working in China network environments where WebSearch is unavailable
- When executing multi-step tasks that need structured progress updates

## Communication Rules

- After every 2-3 tool calls, output a brief status update describing what was done and what's next
- Before executing long-running operations, inform the user about the estimated scope
- Never process more than 3 steps silently — always pause to share progress
- When a task involves multiple subtasks, list the plan first, then report after each subtask completes
- If waiting for user input or encountering ambiguity, ask immediately instead of guessing silently

## Task Execution

- Break large tasks into smaller steps and report progress incrementally
- Use verbose output mode when running build/test commands so the user sees real-time feedback
- If a command takes more than 10 seconds, explain what's happening while waiting

## Tool Restrictions

- WebSearch tool is unavailable in China network, DO NOT use it
- If network information is needed, ask the user to search manually or provide the content directly

## Best Practices

1. **Communicate proactively** — don't let the user wonder what's happening
2. **Report early and often** — 2-3 tool calls max before a status update
3. **Plan before executing** — list the plan, then execute step by step
4. **Respect network constraints** — never rely on WebSearch, ask the user instead
5. **Be transparent about wait times** — explain long-running operations

## Common Pitfalls

- Going silent for multiple steps without updating the user
- Using WebSearch without considering network availability
- Executing large tasks without breaking them down first
- Not informing the user before long-running operations

1. **P0｜额度语义与失真控制**
   - 主圆环采用 **周额度剩余比例**：`max(0, 1 - weekly_usage_usd / weekly_limit_usd)`，最符合现有“剩余递减”语义。

   - `daily_limit_usd=0 + mode=unrestricted` 应解释为**无日限额**，绝不能画成 0%。
   - 主轨不展示今日比例；hover 单独显示“今日已用 `$cost` / `requests` 次”，日限额显示“无限制”或 `∞`。
   - `weekly_limit<=0`、字段缺失或解析失败时统一显示虚线空环；不要把今日费用或月额度临时替代为周比例。

2. **P0｜配置、密钥与 URL 安全**
   - 使用 `tomllib` 严格读取 `model_providers.OpenAI.base_url`，`json` 读取 `OPENAI_API_KEY`；分别区分配置缺失、密钥缺失、401/403、超时、5xx、JSON/schema 异常。
   - 延续现有策略：仅允许 HTTPS、明确域名白名单、解析并拒绝全部私网/回环/link-local/reserved IPv4/IPv6。
   - **禁止自动重定向**，避免 Bearer 密钥被带往其他主机；开启证书校验，设置连接/读取超时及响应体大小上限。
   - URL 应结构化拼接，避免 `urljoin()` 吞掉 `base_url` 路径；明确兼容 base 是否已含 `/v1`。
   - 失败后圆环立即变为“未知”，hover 显示错误类型和最后成功时间；旧读数最多只能作为明确标注的“上次数据”，不能继续画成实时圆环。日志中不得输出 key。

3. **P1｜周重置时间**
   - 当前可推算为 `weekly_window_start + 7天`；示例是 **2026-09-28 00:00:00+08:00**。
   - 风险包括：后端实际采用滚动窗口、结算延迟、窗口规则调整，以及 ISO 时间只有固定 `+08:00` 偏移而非完整时区规则。
   - UI 应写“**预计重置**”，不要写成确定承诺；保留源时间偏移，禁止先去掉时区再计算。
   - 到达推算边界时不要本地把圆环重置为 100%；立即重新请求。若服务仍返回旧窗口，则显示未知/等待结算。
   - 最稳妥方案是推动接口增加 `weekly_window_end` 或 `reset_at`，客户端优先使用服务端显式字段。

4. **P1｜四槽布局**
   - 保持原密度时从 `44×232` 增至约 `44×307` 是合理且风险最低的方案，不建议为了保持高度而明显压缩图标和数字间距。
   - 建议动态计算高度，而非写死：上下边距 + 各槽固定高度 + 槽间距。
   - 可将 GLM、Kimi、Codex 作为“额度组”，番茄钟前增加约 `6–8px` 分组间距；无需添加文字标题或分隔线，44px 宽度承载不了。
   - 若必须紧凑，可压至约 `288–296px`，但应优先保证百分比数字不重叠，并验证 Windows 125%/150% DPI。

5. **P2｜图标与配色**
   - 12px 下“六圆叠加＋中心打孔”容易变成模糊花朵或齿轮，轮廓不够稳定。
   - 建议用 PIL 在 4×或 8×尺寸绘制简化六瓣结，再用 LANCZOS 缩小；最细结构至少保留约 `1.25–1.5` 个最终像素。
   - 不必追求完整 Logo 细节，优先保证六瓣旋转结构和中心负形；在 100%、125%、150% DPI 下截图验证。
   - 正常色建议采用高亮中性银灰/冰白，例如 `#D6DCE5`，符合 OpenAI 单色识别，也能避开现有蓝、绿、紫、teal及告警色；异常状态仍统一使用系统告警色。
